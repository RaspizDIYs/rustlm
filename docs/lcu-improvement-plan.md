## Архитектура и общие условия

- `riot_client` — единственный транспорт LCU: авторизация, лимиты, таймауты, диагностика. Без второго HTTP/WS-движка.
- `lcu_protocol` и политика автоматизации — разбор внешних данных и решения; без файлов, сети и UI в чистой логике.
- `auto_accept` — исполнение решений, отмена и проверка результата; события и polling используют один путь.
- Сервисы входа, Configs, Unglitch и Repair Tools сохраняют ответственность за свои операции. UI вызывает команды и показывает фактический результат.
- Ответ старого подключения не меняет состояние нового. Смена аккаунта/сессии отменяет устаревшую работу. Блокировки не удерживаются на время неограниченного сетевого ожидания.
- Записи не повторяются вслепую: после неоднозначного ответа сначала читается фактическое состояние. Ограничены очередь, ожидание, повторы, объём записи и срок хранения.
- Нет паролей, токенов и личных данных в фикстурах/отчётах. Изменение файлов — временный файл, проверка, атомарная замена и пригодная для отката копия.
- Проверки строятся на поведении: входные состояния → команды и итог; обязательны негативные утверждения об отсутствии лишних записей.

## Порядок выполнения

### 1. Надёжное воспроизведение и контракты — основа и CLI проверены, остаётся расширение записей

Места: `scripts/lcu-replay*`, `scripts/lcu-simulator*`, `services/session_recording`, `services/lcu_protocol`, тесты транспорта.
Источники: winer, ninja-recorder, otp_lol, lol-draft-helper, lcu-and-riotclient-api.

1. Укрепить существующий replay: время, порядок команд, обрывы, повторное подключение, некорректные записи, завершение.
2. Добавить проверенные обезличенные реальные payloads с версией клиента, происхождением, лицензией и контрольной суммой. Синтетические помечать отдельно.
3. Проверять неизвестные/отсутствующие поля, варианты Create/Update/Delete, отсутствие лобби и изменения схем. Не расширять сбор персональных данных ради удобства тестов.
4. Дать каждому сценарию ожидаемые команды, запрет лишних команд и конечное состояние; непотреблённые действия означают провал.

Готовность: ранняя/повторная/неверная команда отвергается без продвижения ожидаемой команды; потеря соединения и восстановление воспроизводимы; тесты запускаются без League.

Источники: winer, hasagi-core, rank-analysis, LeagueAkari, lol-record-assistant.

Не смешивать лимиты LCU, Riot Web API и GoodLuck. Повторы GET ограничены; 404 отсутствующего ресурса не превращается в бесконечный reconnect. Для 429 учитывать доступный Retry-After и предел ожидания.

Проверки: старый 401 после новой авторизации; одновременные GET; занятая очередь; отмена; 429; malformed JSON; отсутствующее лобби; reconnect без двойного действия.

## Сквозная проверка backend и эксплуатации

Эти требования применяются к каждому этапу до его закрытия, а не откладываются на финальный релиз.

### A. Простые проверки: вход, контракт, ошибки

- На границе Tauri/HTTP/WS/файла проверять тип, размер, диапазон, версию и сочетания полей. Некорректное состояние не превращать в разрешённое действие через значение по умолчанию.
- Таблица результата операции: выполнено, ожидается, отменено, не поддерживается, ошибка, результат неизвестен. Timeout записи означает неизвестный результат до сверки, а не гарантированный отказ.
- Одна ошибка пользователю; технические подробности в отчёте с кодом причины и безопасным контекстом. Пароли, заголовки авторизации, recovery-коды, чат и полный сетевой дамп не логировать.
- Тестировать пустые/неполные/слишком большие данные, нулевые идентификаторы, неизвестные enum, неподдерживаемые версии и неожиданные комбинации method/event.

### B. Средние проверки: жизненный цикл и восстановление

- Для каждого исполнителя описать состояния, переходы и владельца операции. Связать операцию с поколением подключения, аккаунтом и игровой сессией; проверять актуальность непосредственно перед побочным эффектом.
- Матрица взаимного исключения: login ↔ login; login ↔ Unglitch; repair ↔ rollback; apply-config ↔ restore. Независимые чтения не должны блокировать готовность/пик.
- Отмена освобождает permit/lock/таймер; повторная отмена и закрытие безопасны. Shutdown перестаёт принимать работу, отменяет ожидания, ограниченно ждёт исполнителей и сохраняет диагностический итог.
- Проверять восстановление после обрыва/перезапуска, а не только первый запуск. Не возобновлять опасную запись автоматически без проверки фактического состояния.
- Файловые операции проверять на отказ доступа, заполненный диск, повреждённую копию, блокировку другим процессом и изменение файла извне. При конфликте не перетирать неизвестные изменения.

### C. Сложные проверки: конкуренция и отказоустойчивость

- Детерминированные перестановки событий: старый ответ после нового; delete после update; reconnect во время записи; два источника одного события; отключение прямо перед POST; потерянный ответ уже выполненной записи.
- Проверять свойства: один побочный эффект на действие; запрещённый чемпион не выбирается; один союзный чемпион не назначается двоим; старое поколение не меняет новое; откат не уничтожает исходник; отменённая операция не выдаётся за успех.
- Использовать контролируемое время/барьеры в логических тестах; реальные таймеры оставить интеграционным. Не лечить нестабильный тест увеличением sleep без причины.
- При нагрузке проверять верхние пределы очереди, памяти записи, числа таймеров и дочерних процессов. Не создавать безграничный журнал действий или отдельный таймер на каждую запись большого trace без измерения.
- Для серверных изменений пати/облака: транзакция, CAS/версия и идемпотентность; конкурентные проверки на настоящем PostgreSQL/Redis, истечение доступа и повторная доставка событий. Изменять backend только при подтверждённом разрыве контракта.

### D. Диагностика и отчёты

Расширять существующий `client_diagnostics`, а не создавать второй журнал. Минимальный отчёт: версия LM, версия формата, время, область, стадия, код причины, HTTP-статус при наличии, длительность, число попыток, итог восстановления и относительный путь к безопасному логу. Для связи событий использовать локальный идентификатор операции без логина/PUUID.

Сбор отчёта локальный, отправка разработчику только по действию пользователя. При недоступности папки отчёта показать отдельную ошибку сохранения, сохранив исходную причину. Ошибку диагностики не отправлять рекурсивно в тот же неисправный канал.

Запись сессий объясняет автоматическую остановку: лимит, время или ошибка диска; причина сохраняется до следующего старта и показывается в UI (исправлено, тесты лимита/ошибки записи прошли). Воспроизведение должно сохранять итог и возвращать ненулевой код при несовпадениях/невыполненных командах. Успешное пустое воспроизведение не доказывает работоспособность автоматизации.

### E. DevOps: проверки, артефакты, выпуск

- Проверить `.github/workflows/verify.yml`, `release.yml` и фактические команды: новые тесты должны запускаться в CI, а не только вручную. Падение/отсутствие обязательного теста блокирует выпуск.
- Фиксировать проверенный commit/tree, команды, итог, число тестов и непроверенные сценарии. Чужой или устаревший зелёный прогон не считать результатом текущего дерева.
- Debug-переопределения LCU и тестовые токены недоступны production. Обезличенные fixtures допускаются; сырые записи, секреты и локальные config не включаются в installer/release assets.
- Проверить установку/обновление, миграции настроек, подпись и updater manifest, запуск без консольного окна и сохранение настроек после рестарта. Версия и changelog соответствуют опубликованным бинарникам.
- Сервер выкатывать штатными скриптами с проверкой нужного image/commit, health и пользовательского сценария. Доступный health не заменяет проверку приглашения/авторизации.
- До выпуска описать откат клиента/сервера и совместимость схемы. Backup без проверенного восстановления не закрывает критерий готовности.

## Учёт выполнения

Каждый этап закрывается записью: изменение → проверка → результат → оставшийся риск. Непроверенный пункт остаётся открытым.

| Область | Проверено в коде | Следующее действие |
|---|---|---|
| Replay | CLI проверен отдельным процессом; 0/1 exit, атомарный отчёт, ошибка сохранения; нагрузка/дубли/таймеры проверены | Расширить реальные записи по режимам и событиям |
| Recorder | Allowlist, общая квота, причина/путь; отказ записи и повторный старт проверены | UI-проверка на реальном диске |
| Диагностика | Уже есть общий `client_diagnostics` | Проследить экспорт и видимость ошибки от сервиса до UI |
| Выпуск | В verify/release добавлены JS/Rust/native integration и SDK runner | Подтвердить выполнение на GitHub runner |

### Выполнено следующим проходом

- Replay: один последовательный планировщик вместо таймера на каждую запись; обработка пакетами до 1000 событий; журнал последних 1000 действий с полным счётчиком ошибок; идемпотентное закрытие. Проверены 5000 одновременных событий, 1005 несовпадений и десять конкурирующих одинаковых записей.
- Три обезличенных upstream fixture winer (PLANNING/BAN_PICK/FINALIZATION), MIT, исходный commit и SHA-256; Rust проверяет маршрутизацию/локального игрока, JS — происхождение, контрольные суммы и отсутствие полей identity/авторизации.
- Recorder ограничивает общий объём папки: 500 МБ с резервом под новую сессию и 1000 файлов. Без автоматического удаления; отказ сообщает причину. Проверены границы и сохранность существующих файлов.
- Транспорт проверяет поколение подключения. Старый успешный ответ не возвращается как актуальный; старая ошибка не сбрасывает даже повторно выданные одинаковые реквизиты нового поколения. Записи не повторяются автоматически.
- 230 Rust-тестов, 95 JS-тестов; отдельно 12 native сценариев + 1 записанный replay прошли. Production-сборка и детали оставшихся проверок фиксируются в отчёте.

Этапы 3–9 не объявляются завершёнными по этим результатам. Следующие действия: проверить таймеры/отмену готовности на поколении игровой сессии, неоднозначный результат записи при потере ответа и согласование группового драфта на расширенных fixture.

Автопринятие дополнительно проверяет ревизии включения и настроек после получения готовности и прямо перед отправкой, включая ожидание очереди. Проверка реализована общим guarded-вариантом существующего транспорта; второй исполнитель не добавлен. Детерминированный интеграционный сценарий удерживает write permits, опрашивает future до Pending, отменяет действие и проверяет отсутствие принятия.

Последний итог: 230 Rust + 95 JS, 13 native integration + 1 replay; production Next.js/TypeScript build успешен. Автоотмена HTTP после ожидания очереди проверена; текущие открытые работы остаются в этапах 2–9 и разделе CLI этапа 1.

### Следующий проверенный проход: подтверждение принятия и CLI

Автопринятие удерживает единственный gate до проверки фактического `playerResponse=Accepted`, в том числе после потери HTTP-ответа. HTTP 200 без эффекта не сообщает успех. Интеграция проверяет потерянный ответ и отсутствие второй команды. Если ready-check уже исчез, эта проверка не приписывает себе подтверждённое принятие; расширенная сверка перехода игровой сессии остаётся открытой.

Replay CLI поддерживает `stop` через stdin для переносимого автоматического завершения. Тест запускает настоящий процесс и проверяет 1 при неполном сценарии, 0 при выполненном, а также 1 при отказе записи отчёта. JSON-отчёт `<config>.report.json` сохраняется через временный файл/rename и не содержит токена. Проверка реального SIGINT Windows остаётся отдельной.

Результат: 230 стандартных Rust passed (16 ignored); 14 native сценариев + 1 recorded replay отдельно passed; 96 JS passed. Этапы 2–9 по-прежнему не закрыты полностью.

### Пакетный проход по переходам и смежным сервисам

Устранён конфликт здорового мониторинга/refresh профиля с поколением подключения. Loadout привязан к ревизии настроек; ошибочный список рун не вызывает мутаций. Общая проверка PersistedSettings применяется во всех путях подготовки/записи пресетов. Подробнее — пакетный раздел отчёта, включая ограничения.

Следующие направления: игровая сессия готовности и UIA; атомарность индекс/файл пресетов; согласование драфта при изменении состава; живые сценарии пати и провайдера.

### Пакетный проход: журнал пресетов и единый отправитель приглашений

Реализован recoverable commit файла и индекса пресета с четырьмя сценариями отказа/конкуренции. Все пути сохранения объединены, экспорт атомарен, чтение восстанавливает незавершённую операцию; повреждённый журнал не сбрасывается молча. Защита действует внутри процесса, выбор личного пресета остаётся отдельным шагом.

Для приглашений после server revision check повторно читается локальное лобби и проверяются identity/phase/leader/queue. Уже присоединившиеся или ожидающие приглашение получатели не отправляются повторно. Создание лобби использует общий отправитель, отдельный дублирующий код удалён.

Отчёт содержит доказательства и остаточные риски. Следующие открытые пункты: транзакционность personal choice, защита между процессами, готовность/UIA по игровой сессии, изменения состава во время draft и реальные сценарии двух LM. Полный план не закрыт.

На Windows добавлен эксклюзивный OS handle `.presets.lock` поверх mutex. Проверяется отказ второго opener и восстановление после освобождения; физический прогон двух EXE остаётся открытым. Выбор личного пресета не включён в общую транзакцию payload/index, остаётся отдельным пунктом.

Финальный результат после Windows OS-lock: полный Rust 238 passed / 20 ignored / 0 failed; JS 96 passed; native отдельно 18 сценариев + 1 replay passed (до добавления OS-lock, native-модули после этого не менялись). Последний полный Rust-прогон включает тест блокировки и финальный общий отправитель приглашений. Реальный клиент/два LM/два EXE не проверены; релиз и серверный выкат не выполнялись.

### Личный выбор, UIA и переходы готовности — реализованы базовые защиты

Выбор личного пресета включён в восстановление журнала; legacy читается и мигрируется, удаление canonical choice не возвращает старое значение. Проверены отказ записи выбора и отсутствие повторного bootstrap. UIA worker удерживает gate до завершения и проверяет lifetime/ревизии перед Invoke; отменённый async waiter больше не разрешает отложенное нажатие. Готовность допускает подтверждённый переход только в ту же известную игру, сохраняя совместимость при недоступном необязательном gameflow. Кэш драфта не откатывается на меньшую ревизию и связывает proof с ролями.

Проверки и ограничения записаны в последнем разделе отчёта. Живое UIA, два EXE/два LM, сценарии провайдера и выполнение GitHub Actions остаются открытыми. Эти результаты не закрывают весь план.

Чтение ответа LCU ограничено 16 МиБ и проверяет UTF-8; тестируются declared/chunked body и точная граница на настоящем loopback HTTP. Незакрытыми остаются отдельные пункты транспорта (объединение одинаковых чтений и политика 429), реальные сетевые/игровые сценарии и выпуск.


### Пакетный проход: общие чтения, 429 и поколение очереди

Транспорт объединяет только одновременно ожидающие GET одного адреса и поколения подключения. Завершённый ответ не кэшируется. Отмена ведущего вызова завершает ожидающих с явной ошибкой, без скрытого повтора; уведомление регистрируется до чтения результата, чтобы не потерять пробуждение. Старое поколение не удаляет состояние нового. Таблица ограничена 128 живыми ключами; при заполнении новые чтения идут через прежнюю ограниченную очередь без объединения.

429 учитывает Retry-After в секундах и HTTP-date; дробный остаток даты округляется вверх, чтобы не отправить запрос раньше срока. Отсутствующее/неверное значение даёт 1 секунду, верхняя граница локальной паузы — 1 час. Пауза привязана к методу, адресу и поколению подключения; не блокирует остальные адреса и не удерживает permit. Повторный ранний вызов сразу получает понятную ошибку 429, автоматического повтора записи нет. Одновременные ответы не сокращают уже установленный срок. Таблица ограничена 128 адресами с вытеснением ближайшего срока при переполнении; это ограничение памяти, не глобальная гарантия подавления всех запросов под произвольной нагрузкой.

Поколение запроса теперь фиксируется до ожидания очереди и проверяется перед отправкой: запрос старого подключения не отправляется с новой авторизацией. После ответа действует прежняя проверка актуальности. Неатомарное окно между последней проверкой и обработкой запроса клиентом Riot остаётся.

Проверки: общий Rust — 249 passed / 23 ignored; отдельно 21 native simulator и 1 recorded replay (expected=1, consumed=1, mismatches=0); JavaScript — 96 passed. Симулятор считает фактические HTTP-запросы: два параллельных GET дают один запрос, завершение не превращается в кэш, отмена ведущего будит ожидающего, GET/POST после 429 не отправляются повторно до срока, другой адрес/метод и новое подключение остаются независимыми. Четыре чистых теста политики проверяют отмену, поколения, сроки и разбор заголовка. Loopback-тест чтения ответа исправлен для Windows: принятый сокет явно переводится в blocking mode; первый общий прогон выявил WouldBlock в тестовом сервере, повтор прошёл.

Эта политика относится к LCU. Лимиты публичного Riot API и GoodLuck не объединялись с ней. Реального клиента и production в этом проходе не было; прежние исторические результаты выше сохранены как история, актуальный срез указан в начале документа.


Итог текущего продолжения: 282 обычных Rust-теста, 26 native LCU, 1 native replay и 1 публичный HTTPS прошли; обе release-конфигурации проверены с --locked. JavaScript: 98 passed. Frontend build повторно не запускался: UI/JS не менялись, диспетчер подтвердил актуальный зелёный результат. Fingerprint исходников до и после финальных проверок совпал. Реальный Riot Client и desktop-перезапуск остаются непроверенными.

### Продолжение: отправка и принятие приглашений

### Итог локального продолжения: последние команды пати и граница отправки

Закрыты оставшиеся прямые production-записи пати: PUT ролей, DELETE исходного лобби и POST создания используют существующий guarded transport. Обработчик роли подтверждает результат в том же лобби; при проверке учитываются собственное членство/gameSummonerId и актуальная пара ролей, без требования лидерства. После async guard транспорт повторно проверяет Retry-After. Явный тип LcuNotDispatched отделяет queue/cooldown/cancel от ошибки уже отправленного запроса, чтобы последующая чужая стадия не засчитывала ложный успех поиска.

Локальная матрица этапов 1–9 сверена с тестами и отчётом; новый код не подменяет живую приёмку. Открытый остаток перечислен в таблице в начале: свежие реальные записи патчей, UIA/игры/кооперация, домашняя сеть и выпускная среда. Финальный результат текущего пакета: 285 стандартных Rust passed, 33 ignored отдельно выполнены (31 native LCU + 1 replay + 1 public HTTPS). После последней правки error/transport полный уже собранный unit-test EXE повторно запущен напрямую: 285/33/0, чтобы старый результат компиляции не выдавался за проверку нового дерева. JavaScript 98 passed, production frontend/TypeScript/static export успешен; обе cargo check --locked --release конфигурации прошли. Fingerprint исходников неизменен до/после финальной сверки. git diff --check без ошибок. Сохранились три прежних dead_code warning.

### Продолжение: сброс разрешения после недоступности

Недоступность отзывает не только snapshot, но и локальное подтверждение драфта. Общий обработчик ошибок snapshot применяется и к ручному обновлению, и к polling. Повторное чтение не восстанавливает proof без подтверждающей стадии. Проверка proof усилена для отсутствующих ID, неоднозначного собственного участника, revoked/offline и смены игровой привязки. Поведение группы при сетевом сбое сохраняется: ошибка не включает одиночный fallback. Предел отменённой async future и живые условия описаны в отчёте.


Проверка пакета восстановления: cargo test --locked — 286 passed / 33 ignored / 0 failed; отдельно 31 native LCU + 1 replay (expected=consumed=1, mismatches=0), публичный HTTPS smoke 1 passed через текущий test EXE. Обе release-конфигурации cargo check --locked успешны. UI/JS и контракты IPC не менялись: предыдущие 98 JS и production frontend build переиспользованы, повторный frontend-прогон не выполнялся. Исходный fingerprint совпал до/после проверок; git diff --check чистый. Релиз и серверный rollout не выполнялись.
