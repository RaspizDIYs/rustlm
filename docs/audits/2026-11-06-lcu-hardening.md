Подтверждённые разрывы:

- Создание/импорт писали payload раньше metadata; удаление уничтожало payload раньше metadata. При сбое между шагами появлялись невидимые файлы или индекс с отсутствующим пресетом.
- Список пресетов автоматически удалял метаданные, если файл не был виден. Ошибка доступа могла стать потерей записи индекса.
- Приглашения проверяли свежую ревизию LM, но могли использовать старый локальный снимок League после сетевого ожидания. Отдельный путь создания лобби дублировал отправку без этих проверок.

Исправления:

- Общий `PresetMutation` и `preset-transaction.json`: журнал сохраняется до изменения данных; восстановление завершает файл и индекс, затем удаляет журнал. Для удаления payload удаляется только после фиксации индекса. Повтор восстановления идемпотентен.
- Один механизм используется при создании, импорте, удалении, сохранении перед guest restore и bootstrap личных клавиш. Чтения восстанавливают незавершённую операцию; повреждённый журнал блокирует изменения и сохраняет исходные файлы. Общий mutex защищает операции разных экземпляров сервиса внутри процесса.
- Автоматическое уничтожение «осиротевших» metadata убрано; отсутствующий файл остаётся диагностируемой проблемой. Экспорт использует существующую атомарную запись.
- Перед приглашением повторно проверяются аккаунт, сервер, фаза, лидерство и то же лобби. Получатели, уже появившиеся в составе или активных приглашениях, исключаются. Начальное создание лобби вызывает тот же общий отправитель; дублирующая реализация удалена.

Проверки:

- 26 тестов `lol_config` прошли, включая четыре новых: interrupted upsert/delete, I/O failure с последующим восстановлением, corrupt journal без перезаписи исходных данных, два конкурентных commit без потери индекса.
- Полный Rust-прогон: 237 passed / 20 ignored; после объединения отправителей повторены 20 party-тестов — passed.
- JS: 96 passed.

Ограничения: mutex не является блокировкой между процессами; два независимых EXE на одной папке требуют отдельной защиты. Сохранение выбора личного пресета остаётся отдельным шагом после commit файла/индекса — при его отказе возможен повтор bootstrap, поэтому сценарий не объявляется полностью транзакционным. Физический power loss не воспроизводился. Между последним чтением лобби и обработкой запроса Riot остаётся сетевое окно; у LCU здесь нет используемого CAS. Новая проверка получателей покрыта unit-тестом, реальная отправка двум LM этим проходом не подтверждается.

Дополнительно: на Windows журнал/индекс защищаются `.presets.lock` с `share_mode(0)`, а не только mutex. Блокировка держится до завершения чтения/commit/recovery, не обнуляет файл и освобождается при drop handle. Тест удерживает первый native handle, проверяет отказ второго доступа и commit без повреждения существующего payload, затем успешный retry после release. На не-Windows межпроцессная эксклюзивность этим механизмом не заявляется. Отдельный физический запуск двух EXE ещё не выполнен.

## Пакетный проход: личный выбор, UIA, готовность и ревизии группы

1. Личный выбор перенесён в `personal-choice.json` в хранилище пресетов и включён в `PresetMutation`. Журнал остаётся до фиксации файла, metadata и выбора. После ошибки записи выбора восстановление завершается до нового bootstrap, без клонирования пресета. Старый файл выбора читается и мигрируется без удаления. Явное очищенное значение null не позволяет вернуть legacy-выбор после удаления выбранного пресета.
2. Selection-only операции записываются в журнал с полным meta/payload снимком. Старый обработчик, не понимающий новый флаг выбора, увидит upsert, а не delete. Это защита данных при чтении старым кодом, но старый EXE не обязан понимать новый canonical choice.
3. UIA: busy gate принадлежит blocking worker до его фактического выхода и затем возвращается для сверки результата. Отмена ожидающего future помечает отдельный lifetime token; поток проверяет его, enabled и ревизии перед Invoke. Настроены существующие Windows UIA connection/transaction timeouts по 500 мс и deadline обхода 2 с. Это не доказательство жёсткой остановки любого неисправного COM provider.
4. Готовность: gameflow читается с ограничением ожидания 500 мс, необязательная недоступность не блокирует валидный ready-check. Когда ready-check исчез, подтверждение по переходу ChampSelect/GameStart/InProgress допустимо только при том же положительном gameId. Другой известный gameId отвергает подтверждение старой попытки. Явно противоречащая исходная фаза не допускает отправку accept.
5. Кэш согласования отвергает меньшую ревизию того же пользователя и группы, не обновляет время её актуальности и не сбрасывает текущее подтверждение из-за старого ответа. Новая группа имеет независимую ревизию. Подтверждение ответа принимается только для текущей группы/ревизии; смена основной/вторичной роли снимает старое подтверждение.

Добавлены проверки: отказ сохранения choice после commit индекса с последующим восстановлением без дубля; миграция legacy без клонирования; отсутствие восстановления старого выбора после explicit clear; UIA cancellation до COM/Invoke; реальный abort async waiter при удерживаемом blocking worker без sleep; переход ready-check в свою/другую игру; rollback ревизии кэша и снятие proof при смене роли. Новый тест кэша выявил отсутствие роли в proof, проверка усилена, а не ослаблена.

Физические ограничения: реального нажатия UIA в League, двух EXE и двух LM на разных ПК не было. При отсутствующем gameId сохраняется прежняя проверка playerResponse=Accepted; положительная привязка к игре возможна только при доступных идентификаторах. Между последней проверкой отмены и вызовом ОС остаётся неатомарное окно, как и между проверкой LCU и обработкой запроса Riot. Сервер и публичный релиз не изменялись.

Дополнительно по транспорту: чтение LCU ограничено 16 МиБ по Content-Length и по сумме реально полученных chunks; некорректный UTF-8 отвергается. Ошибка учитывается общей диагностикой без сырого body, permit освобождается при возврате ошибки. Loopback HTTP-тест проверяет declared oversize, chunked oversize, точную границу и неверный UTF-8, используя малые payloads вместо нагрузки на память машины. Автоматические повторы записей не добавлялись.


### Пакетный проход: общие чтения, 429 и поколение очереди

Транспорт объединяет только одновременно ожидающие GET одного адреса и поколения подключения. Завершённый ответ не кэшируется. Отмена ведущего вызова завершает ожидающих с явной ошибкой, без скрытого повтора; уведомление регистрируется до чтения результата, чтобы не потерять пробуждение. Старое поколение не удаляет состояние нового. Таблица ограничена 128 живыми ключами; при заполнении новые чтения идут через прежнюю ограниченную очередь без объединения.

429 учитывает Retry-After в секундах и HTTP-date; дробный остаток даты округляется вверх, чтобы не отправить запрос раньше срока. Отсутствующее/неверное значение даёт 1 секунду, верхняя граница локальной паузы — 1 час. Пауза привязана к методу, адресу и поколению подключения; не блокирует остальные адреса и не удерживает permit. Повторный ранний вызов сразу получает понятную ошибку 429, автоматического повтора записи нет. Одновременные ответы не сокращают уже установленный срок. Таблица ограничена 128 адресами с вытеснением ближайшего срока при переполнении; это ограничение памяти, не глобальная гарантия подавления всех запросов под произвольной нагрузкой.

Поколение запроса теперь фиксируется до ожидания очереди и проверяется перед отправкой: запрос старого подключения не отправляется с новой авторизацией. После ответа действует прежняя проверка актуальности. Неатомарное окно между последней проверкой и обработкой запроса клиентом Riot остаётся.

Проверки: общий Rust — 249 passed / 23 ignored; отдельно 21 native simulator и 1 recorded replay (expected=1, consumed=1, mismatches=0); JavaScript — 96 passed. Симулятор считает фактические HTTP-запросы: два параллельных GET дают один запрос, завершение не превращается в кэш, отмена ведущего будит ожидающего, GET/POST после 429 не отправляются повторно до срока, другой адрес/метод и новое подключение остаются независимыми. Четыре чистых теста политики проверяют отмену, поколения, сроки и разбор заголовка. Loopback-тест чтения ответа исправлен для Windows: принятый сокет явно переводится в blocking mode; первый общий прогон выявил WouldBlock в тестовом сервере, повтор прошёл.

Эта политика относится к LCU. Лимиты публичного Riot API и GoodLuck не объединялись с ней. Реального клиента и production в этом проходе не было; прежние исторические результаты выше сохранены как история, актуальный срез указан в начале документа.

## Продолжение: identity, RSO и безопасная остановка входа

1. Подтверждение login расширено: помимо существующих authorization/LCU ответов параллельно читаются `/riot-client-auth/v1/userinfo`, `/rso-auth/v1/authorization/userinfo` и `/rso-auth/v1/session`. Маршруты сверены с [каталогом Riot Client API](https://github.com/KebsCS/lcu-and-riotclient-api/blob/main/riotclient/data.json). Это каталог reverse-engineered API, не гарантия ответа текущего клиента на домашнем ПК. Каждый RC-запрос identity ограничен 2 секундами. Поддерживаются объект userInfo и JSON-строка внутри userInfo; auth hints/displayName не принимаются за login. Противоречивые имена и смена поколения отвергаются; содержимое identity/token не записывается в отчёт. Неизвестный login по-прежнему не превращается в успешную авторизацию.
2. RSO теперь различает `Some(true)`, `Some(false)` и `None` по явным признакам. Пустой `{}`, error-пакет, неизвестный type и противоречивые флаги не подтверждают выход. Поддерживаются authenticated, needs_credentials/password/multifactor, пустое значение error не считается ошибкой. Используются зарегистрированные GET v1/riot-client-auth/session, а не несуществующий GET коллекции v2/authorizations.
3. Таймауты ожидания RC API и RSO охватывают весь цикл, включая зависший HTTP-запрос. Ранее проверка deadline происходила только после HTTP-ответа и могла превысить заданный срок. Ожидание identity/RSO в login отменяется общим cancellable helper; отмена имеет приоритет даже над одновременно готовым результатом.
4. Ручные Reload/Hide/Restore Unglitch проверяют свежую фазу и тот же backend PID после write queue. Переход Lobby→ChampSelect без подтверждения не даёт отправить старую ручную команду; смена/отсутствие PID также отменяет отправку. Автоматический путь сохраняет собственные строгие условия.
5. После hard cleanup проверяется завершение RC и League backend/UI. Если 10 секунд истекли, вход возвращает ошибку, не продолжая новую очистку файлов сессии и повторный запуск. Проверка отмены общая с сетевыми ожиданиями. In-memory/файловое восстановление гостевого режима остаётся в существующем lifecycle.
6. Ошибки проверки identity сформулированы без ложной фразы «запуск отменён»: они могут возникнуть и при финальной сверке после открытия продукта.

Добавлены чистые проверки parser/cancellation/process timeout и два native simulator сценария: userinfo fallback + жёсткие RC/RSO deadlines; manual Unglitch dispatch confirmation/PID. Перед окончательной текстовой правкой прошли 282 стандартных Rust и 26 native + replay; окончательные результаты следующего прогона указаны в актуальном срезе.

## Продолжение: запуск и отмена поиска пати после очереди

Подтверждённый разрыв: `party_queue` и `party_cancel_queue` проверяли локальное лобби до ожидания write permits. Пока запрос ждал очередь, League могла сменить фазу, аккаунт, лобби, лидерство, состав или роли. GET-проверка перед очередью не защищала отправку старого POST/DELETE.

- Запуск использует существующий `lcu_post_checked`, отмена — тонкий `lcu_delete_checked` поверх того же транспорта. Перед отправкой заново читается локальное состояние; проверяются fingerprint лобби, summoner/server/PUUID, фаза, лидерство и состав; для запуска также полное присутствие участников и реальные роли League.
- Если guard отменил запуск до отправки, LM завершает серверную попытку с success=false и возвращает исходную ошибку. Поздний ReadyCheck, созданный другим действием, не подтверждает эту отменённую попытку. Неоднозначные ответы уже отправленной команды сохраняют прежнюю сверку без слепого повтора.
- Весь `read_local` ограничен 3 секундами, включая HTTP и дополнительные чтения ранга/автоматизации; ранее elapsed проверялся только после части последовательных запросов. Между началом и концом проверяются поколение подключения и фаза gameflow. Это не атомарный снимок Riot: изменение сразу после последнего чтения возможно.
- Чистый тест покрывает изменения фазы/аккаунта/сервера/лобби/лидерства/состава/ролей. Native loopback тест удерживает оба write permits, меняет фазу на ReadyCheck, затем проверяет отсутствие фактических POST и DELETE поиска и неизменность actions. Это тест реального транспорта с синтетическими ответами, не League.

Ограничения: локальный guard не блокирует внешние действия в League; между проверкой и обработкой команды Riot остаётся окно. Серверная ревизия не блокируется на время локальной очереди. Полный сценарий двух LM, задержки реального клиента и поведение UI требуют домашней проверки. Новые зависимости, изменения UI и публикация не добавлялись.

## Продолжение: приглашения после ожидания очереди

У отправки приглашений и обоих путей их принятия оставалось окно между preflight и отправкой: write queue могла задержать команду до смены группы, аккаунта, стадии или отзыва приглашения. Общий транспорт уже поддерживал async guard, но эти вызовы его не использовали.

1. Отправка `/lol-lobby/v2/lobby/invitations` теперь повторно читает серверную группу после write queue: id/revision/state/leader/queue должны соответствовать исходным, лидерство — сохраняться. Проверяются прежний локальный аккаунт и fingerprint лобби, состав и отсутствие каждого адресата среди уже приглашённых/присоединившихся. Если хотя бы один адресат изменился, весь устаревший пакет не отправляется; следующий штатный snapshot заново вычисляет оставшихся получателей.
2. Ручное принятие и присоединение с переключением аккаунта используют один `accept_league_invitation`. Перед POST проверяются актуальная ревизия группы, accepted-членство с тем же gameSummonerId, сервер лидера и локального аккаунта, отсутствие другого лобби и тот же Pending invitation с возможностью принятия.

## Финальная локальная сверка: роли, выход, создание лобби и 429

- Все production-вызовы записи пати проходят через общий guarded transport. У двух путей выхода из лобби проверяется тот же локальный аккаунт/fingerprint и idle-фаза после write queue; новый ReadyCheck/лобби отменяет старый DELETE.
- Синхронизация ролей использует checked PUT. Проверяются исходное лобби, членство/gameSummonerId, режим с выбором ролей, нужная пара ролей и актуальная серверная revision. Лидерство для смены собственных ролей не требуется. После ответа подтверждаются роли в том же лобби/аккаунте, а не любое совпадение значений в новом лобби.
- Создание лобби повторно проверяет forming-группу с тем же лидером/режимом/revision и отсутствие локального лобби. Сверка аккаунта до создания расширена с summonerId до PUUID/сервера. При ручном переходе после preflight старый POST не отправляется.
- Исправлена гонка cooldown: другой ответ мог установить Retry-After, пока async guard первого запроса читал состояние. Теперь пауза повторно проверяется после guard и до request.send. Native тест удерживает guard через oneshot, получает 429 вторым запросом того же клиента, затем доказывает, что первый запрос не добавил HTTP-обращение.

Пати не пытается подтвердить успех чужим ReadyCheck после queue timeout, отсутствующей авторизации, cooldown или отмены guard. Неоднозначная ошибка после отправки остаётся отдельным случаем и сверяется без слепого повтора.

Новые тесты: собственные роли без лидерства, смена членства/пары/режима/фазы, нативные запреты PUT ролей/DELETE лобби/POST создания после изменения фазы и конкурентный cooldown. Проверки выполнены без настоящего клиента, с явными синтетическими ответами и подсчётом HTTP-команд.

## Продолжение: жизненный цикл подтверждения согласованного выбора

При unavailable очищался только snapshot, а confirmation сохранялся. После нового чтения тех же данных прежнее локальное подтверждение могло снова считаться действующим. Это не доказывает ошибочный пик в реальной игре: дальнейшие проверки identity/lease/кандидатов сохранялись. Граница разрешения теперь строже — сбой отзывает и данные, и подтверждение; свежий GET не восстанавливает разрешение сам по себе, требуется повторная подтверждающая стадия существующего процесса.

- Cache.invalidate сбрасывает оба поля; повторный вызов безопасен. Флаг наличия группы при сетевой ошибке сохраняется, чтобы не включить несогласованный fallback.
- Все ошибки snapshot сбрасывают согласование через общий wrapper. Убран повторный сброс только в фоновом loop; ручной IPC и background используют одинаковую политику ошибок. При отмене самой async future этот wrapper не обещает немедленного сброса; остаётся прежний срок свежести кэша.
- Подтверждение требует непустых ID группы и актёра, ровно одного собственного участника, accepted/online и прежней привязки gameSummonerId/server/PUUID. Ревизия и intent/роль/choice проверяются как раньше. Пустые/null идентификаторы больше не проходят через равенство двух null.
- Новый тест на локальном Cache проверяет повторную invalidation и отсутствие восстановления proof после свежего чтения. Существующий тест подтверждения расширен случаями malformed ID, duplicate own member, offline/revoked membership и изменившейся игровой привязки. Глобальный кэш между параллельными тестами не используется.

UI, серверная схема и зависимости не менялись. Живая приёмка/выпуск остаются отдельными; это усиление локальной границы допуска, а не доказательство наличия прежнего сбоя в матче.


Проверка пакета восстановления: cargo test --locked — 286 passed / 33 ignored / 0 failed; отдельно 31 native LCU + 1 replay (expected=consumed=1, mismatches=0), публичный HTTPS smoke 1 passed через текущий test EXE. Обе release-конфигурации cargo check --locked успешны. UI/JS и контракты IPC не менялись: предыдущие 98 JS и production frontend build переиспользованы, повторный frontend-прогон не выполнялся. Исходный fingerprint совпал до/после проверок; git diff --check чистый. Релиз и серверный rollout не выполнялись.


## Продолжение: отмена future во время проверки пати

Закрыт остаток предыдущего прохода: wrapper сбрасывал разрешение только при возвращённом Err; drop/abort ожидающей future не возвращает Err и обходил этот код. Подтверждение могло оставаться доступным до прежнего срока свежести. Это окно локального жизненного цикла, а не подтверждённый ошибочный пик в матче.

SnapshotAttempt отзывает snapshot и confirmation при выходе без успешного завершения: Err, drop/abort и unwind. Успешная операция явно отмечается complete и не стирает обновлённое подтверждение. Во время await mutex не удерживается; таймеров, потоков и зависимостей не добавлено. Флаг группового режима сохраняется, чтобы отмена не разрешила одиночный fallback.

Тест использует отдельный Mutex<Cache>, доводит future до Pending, проверяет наличие proof, удаляет future и проверяет очистку обоих полей. Затем проверяет успешное завершение с новым proof и обычный выход без complete. Глобальный runtime cache тестами не меняется.

Прежний абзац о задержанном сбросе при отмене описывает историческое состояние до этого пакета; с текущим guard этот остаток закрыт. Общая граница остаётся: уже отправленный HTTP-запрос нельзя отозвать на стороне Riot, и его результат нельзя гарантировать одним локальным Drop.


Проверки пакета отмены: 287 Rust passed / 33 ignored / 0 failed; все ignored отдельно выполнены — 31 native LCU, replay (expected=consumed=1, mismatches=0) и HTTPS smoke. Обе release-конфигурации Rust прошли с --locked. Исходники до/после финального прогона совпали. UI/JS не менялись; предыдущие 98 JS и frontend build переиспользованы. git diff --check без ошибок, три прежних dead_code warning сохранены. Публикация, installer и живой клиент не проверялись этим пакетом.
